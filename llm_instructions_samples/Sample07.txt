# Issue 2 — Large text files partially load, keep loading while idle, never finish, and cannot be edited

## Problem

Large text files partially work, but the viewer keeps trying to load even when the scrollbar is not touched. The file never finishes cleanly, and editing still does not work.

Known prior symptom example:

```json
{"command":"fs.text.chunk","id":"fs-17","offset":0,"size":2411725,"event":"desktop.command","requestId":"ws-17-1778043237391"}
```

The chunk size is too large for the current socket/control path. A value around `2411725` bytes appears to be a threshold-sized request, not a safe chunk-sized request.

## Key design distinction

Do **not** confuse these two values:

1. **Text virtualization threshold** — the file size at which the viewer switches from normal editable text mode to chunked/virtual large-file mode. This can remain around 2.3 MB or be made configurable.
2. **Text chunk request size** — the number of bytes requested per chunk. This should be much smaller than the threshold and should be configurable. Use a safe default such as 64 KB, 128 KB, or another source-verified safe size.

## Requirements

### Viewing large files

- Large text files must be viewable without socket errors.
- Opening a large file should request only the initial chunk unless the user scrolls or explicitly requests more.
- The viewer must not continuously load/preload/retry chunks while idle.
- The file must not try to “finish loading” the entire content into the browser for huge files.
- No automatic neighbor prefetch unless it is explicitly bounded, deduped, and does not run while idle.
- Identical chunk requests must be deduped by file id + offset + size.
- Failed chunk requests must not create infinite retry loops.
- Socket timeout/error must show retry/toast feedback and must not break the viewer.
- Avoid whole-file `/api/mioos/fs/blob` fallback for large text.
- If WebSocket cannot safely carry chunks, add a backend HTTP text-chunk/range endpoint that returns only the requested chunk and use it as a fallback.

### Scrollbar behavior

- Scrollbar must map smoothly to byte offsets.
- Scrolling should load the target byte offset, not continuously fetch unrelated chunks.
- Do not jitter or fight the browser’s native scroll behavior.
- Do not reload the same chunk repeatedly when the scrollbar has not moved.
- Debounce/coalesce scroll events carefully.

### Editing large files

Editing behavior must be deliberately designed, not half-broken.

Acceptable designs:

1. **Small/medium editable mode**
   - Files under a configurable edit threshold load into an editor and can be saved.
   - Save clears stale chunk/read cache and reloads the saved content.

2. **Large bounded-edit/read-only mode**
   - Files above the safe edit threshold are viewable through chunks.
   - If full random-access editing is unsafe, show a clear message that large files are read-only or limited-edit.
   - Do not show broken edit/save buttons for unsupported large-file edit mode.

3. **True large-file edit mode**, only if implemented safely
   - Requires deterministic chunk patch/save semantics.
   - Must include backend tests for partial writes, conflict handling, cache invalidation, and MAXSTRING safety.

Do not claim large-file editing works unless it truly works end-to-end.

## Required tests for Issue 2

Add tests in `routines/MIOOST.m` or helper routines if needed.

Tests should include:

### Config/contract tests

- Text virtualization threshold and text chunk size are separate settings.
- Default text chunk size is far below the virtualization threshold.
- Default `fs.text.chunk` request size is not `2411725` or any threshold-sized value.
- Chunk size is MAXSTRING-safe.

### Frontend static contract tests

- Large text open initializes only one initial chunk request.
- No automatic neighbor prefetch while idle.
- No idle auto-load loop.
- No retry loop after chunk failure.
- Chunk request dedupe key includes file id + offset + size.
- Scroll handler is debounced/coalesced and loads target offset only.
- Timeout/catch path shows toast or retry feedback.
- No uncaught Promise path for socket timeout.
- No whole-file blob fallback for large text.
- Small-file edit/save controls still exist.
- Large-file unsupported edit mode is clearly shown or hidden, depending on design.
- Save clears stale text chunk cache.

### Backend contract tests

- `fs.text.chunk` or the current backend chunk route returns only requested chunk bytes.
- Offset 0 returns first chunk only.
- Middle offset returns correct byte range.
- End offset handles EOF correctly.
- Invalid id returns deterministic error JSON.
- Invalid offset/size clamps or rejects deterministically.
- Chunk route does not materialize the entire file into one string.
- Save route works for small/medium files.
- Large save path is rejected with clear deterministic message if large edit is unsupported.

### Performance/MAXSTRING tests

- Test synthetic text data with:
  - small file
  - threshold-minus-one file
  - threshold-plus-one file
  - multi-chunk large file
  - very long line crossing a chunk boundary
- Assert no single chunk exceeds safe configured limit.
- Assert no WebSocket payload concatenates a huge file.
- Assert repeated same-offset request returns cached/in-flight result where applicable.
